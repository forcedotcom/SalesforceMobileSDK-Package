# Cordova upgrade validation

Validate the platform, native engine, bundled JavaScript and SDK/plugin sources as a matched set. A focused native test pass or an unsigned archive establishes only the configuration exercised; record authenticated, device and CI results separately.

## Native test prerequisites

In the SalesforceMobileSDK-iOS-Hybrid repository, use the configured SalesforceHybridSDK test host in `SalesforceMobileSDK-Hybrid.xcworkspace`. Cookie tests write dummy tokens through the real keychain and require the host's keychain entitlement. Simulator entitlements must be present in the simulator executable, as generated by Xcode; ad hoc code signing alone does not supply them. Relative-URL and remote-start-page tests also require a managed current user with instance credentials. An empty host can otherwise produce missing-token assertions or nil-URL exceptions before exercising the intended behavior.

For an isolated host, register a synthetic account through the SDK test account-management setup and preserve an assignment-specific bundle/keychain namespace. Synthetic accounts classify local URL and cookie behavior; they do not establish successful Salesforce authentication. Keep real credentials in excluded, access-restricted fixtures and keep raw authenticated logs and result bundles private. Export only test identifiers, counts and redacted error categories.

The controller suite covers default and custom UI delegates, ordinary custom-controller teardown, callback forwarding and Cordova's cold-link buffering. Cold-link tests supply scene connection inputs and verify deferred, single delivery after page load, plus cancellation on scene disconnect. They do not establish operating-system universal-link association or device callback routing.

## Consumer matrix

1. Generate fresh `hybrid_local` and `hybrid_remote` iOS apps using the reviewed Package CLI and plugin revision. Select compatible SDK sources before the first plugin installation, which already runs CocoaPods.
2. Verify the installed Cordova platform version, native pod/package revision and JavaScript runtime agree. Record the exact Hybrid and plugin revisions; use immutable references for the release set.
3. Exercise first installation, repeated prepare, pod-bearing plugin add/remove, prepare after removal and iOS platform recreation. Confirm `use_frameworks!`, the SDK deployment target and the full resolved pod graph survive completed prepares. Restore erased custom Podfile arguments from their original configuration rather than inferring them from `pods.json`.
4. Build and run both generated apps on the supported simulator matrix. Check scene startup/resume, default/custom delegates, the JavaScript/native bridge and cold scheme delivery. Use an associated-domain test host and assigned device to verify actual universal-link routing.
5. Run an approved authenticated matrix: local and trusted remote content, OAuth callback, refresh, account switch, logout, cookie refresh and local storage/sync behavior. Do not send account-changing or data-mutating requests unless the test scope permits them. Use a supported DPoP login when the client requires DPoP; legacy instant-login test helpers do not establish this coverage, and a refresh token alone does not substitute for its required proof/key context.
6. Archive both apps in Release for a generic iOS destination. An unsigned archive checks device compilation and packaging, while provisioning, signed export, installation and physical-device behavior remain separate checks. Run the supported Xcode/iOS CI matrix before release approval.

Record failures and unavailable matrix entries explicitly. Do not turn excluded or unexecuted cases into a full-suite pass.
